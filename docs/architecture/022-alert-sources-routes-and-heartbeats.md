# ADR-022 — Alert sources, routes and heartbeats

- **Status:** Accepted
- **Date:** 2026-10-20

- **Context:** Until now incidents came from one place: error traces polled from Jaeger. Teams run Prometheus, Grafana, Sentry, Datadog, cron jobs and home-grown checks, and each speaks a different payload format. Not every alert should page anyone or open an incident, and one failure usually fires several alerts at once. This is the entry point for on-call (Phase 11) and the rest of the response product (docs/research/incident-io-feature-map.md).
- **Decision:**
  - *Sources are integrations with a token.* An alert source is an `integrations` row (`provider = alert_source`, `config.kind`), so it reuses the secret store, revocation and the durable inbound buffer. Tools like Alertmanager and Sentry cannot sign requests, so intake authenticates with a per-source token (`ape_alert_…`) sent as `Authorization: Bearer`, `X-Ape-Token` or `?token=`. The token is compared in constant time and shown once; it can be rotated, and disconnecting deletes it. Unknown sources and bad tokens get the same 401 and an audit record, so ids cannot be probed.
  - *One pipeline.* `POST /ingest/alerts/:sourceId` only buffers the body into `inbound_events` (`source = alert:<kind>`, id = SHA-256 of the body, so retried requests are dropped). The existing processor hands those rows to `AlertProcessor` inside its transaction, with the same retries, dead-letter queue and replay as Phase 3.
  - *Parsers per tool, one shape.* `alerts/parsers.ts` turns generic JSON, Alertmanager and Grafana (one webhook shape, batches split into alerts), Sentry (issue and event alerts) and Datadog (documented webhook template) into `ParsedAlert {dedupKey, status, title, description, severity, labels, sourceUrl, occurredAt}`. Severity vocabularies (P1, fatal, warning, info…) map onto ours. Labels are flattened to bounded strings so they are safe to show, filter and group on.
  - *Alert lifecycle.* Alerts upsert on (source, dedup key). A repeat of a firing alert only bumps `occurrences` and `last_fired_at`, with no timeline noise. A resolved notification resolves it. Firing again after resolving re-opens the same row and routes it again.
  - *Ordered routes.* `alert_routes` are evaluated top to bottom, and the first enabled route whose sources and conditions all match wins. Conditions look at `title`, `description`, `severity`, `status` or `label.<name>` with eq, neq, contains, not_contains, regex (validated, length-bounded, case-insensitive), exists and not_exists. A route either opens incidents or only records. An alert with no matching route is still kept and visible, never dropped.
  - *Grouping.* A route's `groupBy` labels form a group key, and the incident fingerprint is `alert:<route>:<hash(key)>`. The existing rule "one open incident per fingerprint" then attaches every alert of the group to that incident while it is open. Without `groupBy`, each alert is its own group. Every timeline entry says why the alert joined ("Grouped by route X on service=checkout"). Incidents get `service`/`env` from labels, so a mapped service brings its repository and the AI investigation. Alerts are collected as investigation evidence.
  - *Resolution does not close incidents.* When all of an incident's alerts resolve, the timeline says so, but the incident stays open: recovery is verified (ADR-019) and a human decides.
  - *Heartbeats.* A heartbeat source expects a ping (`GET` or `POST /ingest/heartbeats/:id`) every `interval + grace` seconds. A checker in the API process marks overdue heartbeats down with a conditional update (safe on several replicas) and buffers a firing alert. The next ping flips the state back with another conditional update, which only one concurrent ping wins, and buffers the resolution. Heartbeat alerts then follow routes like any other.
  - *Preview.* `POST /alert-routes/preview` parses a sample payload and shows each alert's route and group without storing anything, so admins can test routes before connecting a tool.
- **Consequences:** Any tool that can POST JSON can open incidents, with dedup and grouping, through the same durable path as traces. Grouping is "while the incident is open" rather than a fixed time window, which is simpler to reason about; a later window or "merge into existing" action can refine it. Escalation from routes to on-call people is the next phase.
