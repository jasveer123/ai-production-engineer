# ADR-020 — Live updates over SSE and outbox-driven notifications

- **Status:** Accepted
- **Date:** 2026-10-20

- **Context:** The dashboard polled every 5 seconds, and nobody heard about an incident unless they had it open. Changes are written by three processes (the API, the Temporal worker and the ingestion loop) through many code paths, so a change feed has to sit below the application code. Notifications go to URLs that users type in, which makes the sender a server-side request forgery target, and a Slack webhook URL is itself a credential.
- **Decision:**
  - *Postgres `NOTIFY` as the change feed, SSE to browsers.* Row triggers on `incidents`, `incident_events`, `investigations`, `fix_proposals`, `validation_runs`, `pull_requests` and `verification_runs` call `pg_notify('ape_changes', {w, t, i})` with only the workspace, table and incident ids. Notifications are delivered on commit, so a rolled-back write never shows up. Each API process holds one `LISTEN` connection (`RealtimeService`, reconnecting with backoff) and serves `GET /workspaces/:id/stream` as server-sent events. Postgres fans out to every listener, so several API replicas work without a broker; Redis Streams/NATS (D-6) stay a Phase 11 question.
  - *Messages carry ids, never data.* The browser invalidates the matching React Query keys and refetches through the normal endpoints, so every read still passes the workspace guard and RBAC. The stream filters by workspace on the server, batches bursts (`REALTIME_BATCH_MS`, e.g. 50 errors become one message), sends a ping every 25 s, and re-checks membership and session every `REALTIME_RECHECK_MS`, closing the stream for a removed member or a revoked session. Polling stays as a fallback: 5 s while the stream is down, 30 s while it is up.
  - *Notification candidates come from a trigger into the outbox.* An `AFTER INSERT` trigger on `incident_events` writes a `notify` outbox row for every `created` and `status_change` event, in the same transaction, but only when the workspace has an enabled channel. No status-change code path can forget to notify. The outbox publisher (Temporal worker process) maps the event to a type (`incident.detected`, `review.requested`, `incident.needs_attention`, `incident.resolved`, `verification.inconclusive`), filters channels by event and minimum severity, and sends.
  - *At-least-once without duplicates.* `notification_deliveries` is unique per (channel, event key). A retry skips channels that already received the event. Network errors, 5xx, 408 and 429 make the outbox row fail and back off (2 s doubling, capped at 10 minutes, via the new `outbox.next_attempt_at`, which also stops one failing row from being retried in a tight loop). Other 4xx, redirects and rejected URLs are permanent: recorded on the delivery and the channel, not retried.
  - *SSRF and secrets.* Channel URLs must be HTTPS without credentials. In production the host is resolved at creation and again at every send, and private, loopback, link-local (cloud metadata), CGNAT and multicast addresses are refused; redirects are never followed and requests time out after 5 s. Development and tests may post to local `http://` receivers. Slack URLs must match `hooks.slack.com/services/…` and are stored in the secret store, shown masked; generic webhooks get a `whsec_` signing secret shown once and are signed like inbound webhooks (`x-ape-signature: sha256=HMAC(secret, timestamp.body)`, plus `x-ape-timestamp` and `x-ape-event`).
  - *Content is minimal.* Messages contain the incident title, severity, status, service and a link; never stack traces, code or evidence. Slack text is escaped so telemetry like `<!channel>` cannot ping a channel or add links.
  - *Settings.* Admins manage channels (create, pause, test, delete) and severity rules; only owners change the PR approval policy (`PUT /settings/approval-policy`), because it changes the approval gate itself (ADR-018). Every change is audited.
- **Consequences:** Dashboards update within about half a second of a commit with no broker to run. A client can miss changes while disconnected; the slow poll catches it up. `NOTIFY` payloads are limited to 8000 bytes, which ids-only messages never approach. Webhook receivers must deduplicate by the payload `id` if they want exactly-once processing, since a lost response can still cause a resend.
