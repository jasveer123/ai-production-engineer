# ADR-021 — Offline evaluation, model comparison and outcome-based quality

- **Status:** Accepted
- **Date:** 2026-10-20

- **Context:** Prompts, models and the evidence collector all change, and "it diagnosed S1 once" is not a measurement. ADR-016 deferred an OpenAI adapter to a model comparison. Model quality also has to be judged on real incidents, where there is no answer key, only outcomes.
- **Decision:**
  - *Frozen cases built from real code.* `tests/evaluation/build_cases.py` generates evidence bundles from demo-shop's source in exactly the format `collectEvidence` produces (error events, trace, deploys, code excerpts with `>>` on the failing line, commits). There are five cases: S1 (null coupon); S1 with a prompt injection in a commit message; S1 with an unrelated deploy minutes before the errors (red herring); S6 (timeout config, same commit redeployed); and a bare 500 with no evidence, where the right answer is to abstain. The machine-readable `answer-key.json` lives in this repository, never in demo-shop, so an investigating model cannot read it.
  - *Same pipeline, explainable scoring.* `python -m ai_worker.evaluation run` sends each case through `run_investigation`, the same prompt, structured output and evidence guard the Temporal activity uses. A hypothesis matches the key when it names one of the scenario's symbols and also points at one of its files or uses one of its keywords, or when it points at a file and uses two keywords. A diagnosis case passes only when the match is hypothesis #1, no hypothesis blames a forbidden cause (the injected one), and hypothesis #1 does not blame the red herring. "Blames" means the summary and suspected file; observations and rationales may mention a cause to rule it out. An abstain case passes when every hypothesis is low confidence. Per model the report gives pass rate, top-1/top-3, abstention, injection resistance, overconfident answers (wrong with high confidence), evidence-guard drops, invalid outputs, errors, cost and p50/p95 latency. `--min-pass-rate` and `--min-top1` turn it into a gate; results are written to `tests/evaluation/results/` (git-ignored).
  - *Pinned, comparable models.* Specs are `anthropic:<model>`, `gemini:<model>` or `openai:<model>`. Gemini's free-tier fallback is switched off during evaluation so one row is one model. The new OpenAI adapter (`llm/openai_provider.py`, Responses API with a strict JSON schema, typed refusal/truncation/rate-limit errors) is only selected with `AI_PROVIDER=openai`, never by `auto`, so adding a key cannot silently change the production model. Unpriced models report cost as "unpriced" rather than $0.
  - *The harness is tested without a model.* `scripted:reference` holds hand-written correct answers (all must pass, which CI checks on every push). `scripted:flawed` holds the mistakes the harness must catch (an invented citation, a followed injection, blaming the latest deploy, blaming unchanged code, an overconfident guess), and all of them must fail. These fixtures are labelled as not being model output.
  - *Online quality from outcomes.* Engineers mark each hypothesis correct, partly or wrong (one verdict per person, engineer role or higher, audited). `GET /workspaces/:id/quality?days=N` and the Quality page combine those verdicts with stored outcomes for incidents created in the window: a funnel (incidents → investigated → fix validated → PR merged → recovered after deploy, from Phase 7), top-1 precision per model (partly counts as half), fix validation rate, final verification outcomes, guard drops, cost and latency.
- **Consequences:** A prompt or model change can be compared on the same evidence before it ships, and production quality is measured by whether incidents actually recovered, not by model confidence. Five cases are a smoke test, not a benchmark; the keyword matcher can be fooled by a vague answer that names the right symbol, so every score keeps the hypothesis text for a person to check. S2–S5 produce no server-error traces yet, so they cannot be cases until latency/Sentry signals are collected.
