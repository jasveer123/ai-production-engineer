# ADR-019 — Recovery verification after the fix is deployed

- **Status:** Accepted
- **Date:** 2026-10-20

- **Context:** Phase 6 ends when the fix's pull request is merged, but a merge is not a recovery: the fix may not be deployed yet, may be deployed and not work, or the error may simply have stopped for another reason (a flag turned off, traffic dropped). Phase 7 has to decide "resolved" from production evidence, without the platform ever changing production itself (ADR-008).
- **Decision:**
  - *Wait for the deploy that contains the fix, not just any deploy.* After the merge the workflow (`verifyRecovery`) looks at deploys of the incident's service and environment from the merge time on. A deploy counts when its commit equals the merge commit, or when GitHub's compare API reports the deployed commit as `ahead` of (or `identical` to) it. The ingestion processor writes a `deploy.recorded` outbox row with each new deploy, and the outbox publisher signals `deployRecorded` to workflows of incidents in `monitoring`; a poll every `VERIFY_DEPLOY_POLL_MS` is the fallback. After `VERIFY_DEPLOY_WAIT_MS` (7 days) without one, the incident becomes `verification_inconclusive`. GitHub failures during the lookup are treated as "not yet", never as a failed workflow.
  - *Measure the incident's own fingerprint.* While an incident is open, new errors with the same fingerprint attach to it, so verification counts the incident's error events after `deploy + VERIFY_GRACE_MS` (rollout time) and compares them with its rate before the deploy (from first seen, at most 24 h back). Traffic to the failing operation (the server span name from the error, e.g. `POST /checkout`) is counted in Jaeger when a Jaeger integration is connected.
  - *A conservative, pure decision* (`verification/recovery.ts`): at least `VERIFY_MIN_ERRORS` (3) errors after the deploy means `not_recovered`. Zero errors means `recovered` only with evidence: at least `VERIFY_MIN_REQUESTS` (20) requests to the operation, or a pre-fix rate that predicts at least 5 errors for the window (the chance of seeing 0 from Poisson(5) is under 1%). One or two repeats, or zero errors with no evidence of traffic, are `inconclusive`.
  - *Cumulative windows with early failure.* Window *n* covers `[deploy + grace, deploy + grace + n × VERIFY_WINDOW_MS]`, so an extension adds data instead of starting over. Interim checks every `VERIFY_CHECK_EVERY_MS` can only conclude `not_recovered`, so a fix that did not work is reported within minutes. After `VERIFY_MAX_WINDOWS` (3) inconclusive windows the incident is left to a human as `verification_inconclusive`. Timing comes from API config through `beginMonitoring`/`startVerification`, so the workflow stays deterministic.
  - *Outcomes map to the existing state machine:* recovered → `resolved`; not recovered → `needs_attention`, with the previous deploy named as a rollback candidate (text only, a human decides); inconclusive → `verification_inconclusive`. Each window is a `verification_runs` row (unique per incident, deploy and window, so activity retries reuse it) with the baseline, the observation and the reason; the result is also a timeline event and an audit record.
  - *Humans stay in charge.* If someone changes the incident's status while verification runs, the next activity sees it has left `monitoring`/`verification_inconclusive` and stops without overwriting it.
- **Consequences:** "Resolved" now means "the error stopped in production after the fix shipped", with the numbers on the incident page. Low-traffic services often end inconclusive; that is intended. Matching by fingerprint misses a fix that turns the error into a different one; that shows up as a new incident instead. Without a deploy webhook the platform cannot verify anything and says so.
