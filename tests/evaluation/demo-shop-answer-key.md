# demo-shop answer key

Ground truth for the [demo-shop](https://github.com/jasveer123/demo-shop) incident scenarios. Used by the evaluation runner (Phase 9) to score investigations: is the true cause in the top-1 / top-3 hypotheses, does the regression test reproduce it, and does the patch fix it without regressions.

Kept here, not in demo-shop, so the AI cannot read the answers while investigating that repo.

| # | Flag / trigger | Root cause (file → function) | Evidence the platform should find | Expected minimal fix | Regression test idea |
|---|---|---|---|---|---|
| S1 | `FF_CHECKOUT_V2` | `api/src/services/checkout.ts` → `discountV2`: `promotions.get(code ?? '') as Coupon` is `undefined` when no (or an unknown) coupon is sent, then `promo.percentOff` throws `TypeError` | 500s on `POST /checkout`; stack trace in `discountV2`; only requests without `couponCode` fail; started with the flag rollout | Return 0 when no code; reject unknown codes with 400 `invalid_coupon` (same as v1) | Checkout with `FF_CHECKOUT_V2` on and no coupon succeeds with discount 0 |
| S2 | `FF_ORDER_ITEMS_INLINE` | `api/src/services/orders.ts` → `list`: N+1, one `getOrderItems` query per order instead of `listOrdersWithItems` | `GET /orders` p95 jumps; trace shows ~N+1 `pg.query` spans per request | Use `store.listOrdersWithItems` (single joined query) | Assert `getOrderItems` is not called per order / call count is constant |
| S3 | `FF_CATALOG_PAGE_NUMBERS` | `api/src/services/catalog.ts` → `list`: `offset = q.page * limit` should be `(q.page - 1) * limit` | `page=1` returns products 13+ (with default size); no errors, wrong data | `offset = (q.page - 1) * limit` | `page=1,pageSize=5` returns ids 1–5 |
| S4 | `FF_ASYNC_PAYMENT_CAPTURE` | `api/src/services/checkout.ts` → `captureAsync`: fire-and-forget `capture()` with no `.catch`; order returned as `paid` before capture; declines become unhandled rejections and orders stay `pending_payment` / reported paid | `unhandledRejection` logs + Sentry events `payment_declined`; 201 responses for orders over $300 | Await capture (or handle failure: mark `payment_failed`, restore stock, report) and never report `paid` before capture succeeds | Declined card → checkout rejects with 402 and stored status `payment_failed`; no unhandled rejection |
| S5 | `FF_STOCK_RESERVATION_V2` | `api/src/services/checkout.ts` → `reserveStockV2`: read-check-write race (`getStock` → `sleep` → `setStock(stock - qty)`), lost updates oversell | Under concurrency, more orders than stock; stock never reaches 0 correctly; no errors | Use atomic conditional `decrementStock` (`… where stock >= qty`) like v1, with compensation on failure | 5 concurrent checkouts on stock 3 → exactly 3 succeed, stock 0 |
| S6 | `PAYMENT_TIMEOUT_MS=5` (bad deploy) | Config, not code: payment timeout set far below gateway latency (40–120 ms) | 504 `payment_timeout` on almost all checkouts right after a deploy marker; code unchanged between releases | Revert config to ≥ 2000 ms (and optionally validate a sane minimum in `config.ts`) | Config schema rejects timeouts below a minimum |
